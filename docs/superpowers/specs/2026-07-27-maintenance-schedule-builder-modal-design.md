# Годовой график ТО — modal-flow и фильтрация оборудования

**Дата:** 2026-07-27
**Статус:** утверждён пользователем

## Контекст

Первая версия конструктора реализована отдельной страницей
`/maintenance-schedule-builder` с ручным preview перед созданием плана.
Целевой UX должен соответствовать create-flow других реестров:

1. Пользователь находится в календаре ППР.
2. Нажимает кнопку «Построить годовой график».
3. Заполняет форму в модальном окне.
4. Нажимает «Создать и рассчитать».
5. Система автоматически проверяет расчёт, создаёт план, генерирует задачи,
   отправляет план на согласование и открывает его detail.

В выборе должны присутствовать только единицы и типы оборудования, которые
реально могут участвовать в расчёте.

## Цели

- Перенести форму конструктора в управляемое `xl`-модальное окно календаря ППР.
- Убрать отдельный пользовательский шаг «Рассчитать».
- Не создавать пустой план: перед сохранением автоматически выполнять
  stateless-preview с теми же параметрами.
- Фильтровать варианты выбора на backend по единому признаку эксплуатационной
  готовности.
- Явно объяснять критерии фильтрации в модальном окне.
- Сохранить автоматическую генерацию задач внутри создания `PprPlan`,
  согласование и переход на существующий detail.

## Не входит в задачу

- История preview-runs.
- Ручное исключение отдельных occurrences.
- Изменение критериев эксплуатационной готовности.
- Изменение legacy-формы создания обычного плана ППР.
- Новые frontend-зависимости.

## Критерии подходящего оборудования

Единица участвует в выборе и расчёте только при одновременном выполнении всех
условий:

1. `status = ACTIVE`;
2. `currentLocationType = DEPARTMENT`;
3. `operationStartDate != null`;
4. существует неудалённый акт ввода в эксплуатацию со статусом `APPROVED`.

Дополнительно применяется существующее ограничение пользователя по
подразделению. Backend остаётся источником истины и повторно проверяет критерии
во время preview и генерации задач.

## Backend-контракт вариантов выбора

Добавить endpoint:

```http
GET /api/v1/maintenance-schedule/options
```

Query-параметры:

- `scopeType=EQUIPMENT|EQUIPMENT_TYPE` — обязательный;
- `departmentId` — опциональный, проходит через `ScopeAccessService`;
- `search` — опциональный поиск по коду и названию;
- `page` — по умолчанию `0`;
- `size` — по умолчанию `20`, максимум `100`.

Ответ — стандартная пагинированная структура:

```json
{
  "content": [
    {
      "id": "uuid",
      "code": "ET-001",
      "name": "Насос",
      "scopeType": "EQUIPMENT_TYPE",
      "eligibleEquipmentCount": 4
    }
  ],
  "pageable": {
    "pageNumber": 0,
    "pageSize": 20
  },
  "totalElements": 1,
  "totalPages": 1,
  "last": true
}
```

Правила:

- Для `EQUIPMENT` возвращаются только подходящие единицы,
  `eligibleEquipmentCount = 1`.
- Для `EQUIPMENT_TYPE` возвращаются только типы, у которых есть минимум одна
  подходящая единица; `eligibleEquipmentCount` содержит их количество после
  department/RBAC-фильтра.
- Сортировка детерминированная: код, название, ID.
- Доступ: `PPR_PLAN_CREATE` или `PPR_PLAN_GENERATE`, а также admin/wildcard.
- Обычный пользователь без подразделения получает `403`.

Backend должен вынести выбор подходящего оборудования в общий компонент,
используемый и options endpoint, и `MaintenanceScheduleService.preview`.
Нельзя поддерживать два расходящихся набора критериев. Для пагинации и
подсчёта типов используется repository-запрос с `EXISTS` по утверждённому акту,
а не N+1-вызовы для каждой строки.

## Modal UX

В `PprCalendarToolbar` остаётся кнопка «Построить годовой график». Она вызывает
callback календаря, а не переходит на отдельную страницу.

`PprCalendarPage` управляет `MaintenanceScheduleBuilderDialog`. Открытое
состояние синхронизируется с query-параметром:

```text
/ppr-calendar?dialog=maintenance-schedule-builder
```

Это сохраняет deep-link и позволяет старой внешней или сохранённой ссылке
открыть нужную модалку. Маршрут `/maintenance-schedule-builder`
перенаправляется на этот URL. Отдельный пункт конструктора в боковом меню
удаляется: основной entry point — кнопка календаря ППР.

В верхней части модалки показывается постоянный информационный блок:

> В расчёте участвует только оборудование, которое активно, находится в
> подразделении, имеет дату начала эксплуатации и утверждённый акт ввода в
> эксплуатацию. Остальное оборудование не отображается и не участвует в
> расчёте.

Для scope «Типы оборудования» добавляется уточнение:

> Показываются только типы, у которых есть хотя бы одна подходящая единица
> оборудования.

Тип отображается как `Код — Название · N ед.`. Для конкретного оборудования
используется `Код — Название`.

Если вариантов нет, вместо обычного пустого списка показывается инструкция
проверить четыре критерия. Ошибка загрузки вариантов показывает retry и не
разрешает submit.

## Workflow создания

Единственная основная кнопка модалки называется «Создать и рассчитать».

Последовательность:

1. Проверить форму и RBAC.
2. Собрать нормализованный `MaintenanceSchedulePreviewRequest`.
3. Автоматически вызвать `POST /maintenance-schedule/preview`.
4. Если `totalOccurrences = 0`, оставить модалку открытой, не создавать план и
   показать причину/диагностику.
5. Создать `PprPlan` из точно того же request snapshot. Backend внутри создания
   повторно рассчитывает occurrences и создаёт задачи.
6. Сравнить `taskCount` с preview `totalOccurrences`; несовпадение показать
   предупреждением, не удаляя план.
7. Создать approval request для `PPR_PLAN`.
8. Инвалидировать plan/task/approval queries.
9. Закрыть модалку и перейти на `/ppr-calendar/{planId}`.

Отдельный вызов `/ppr-plans/{id}/generate` не выполняется.

При ошибке preview или создания введённые значения сохраняются. Если план
создан, но approval не отправлен, открывается detail с предупреждением и
существующей `ApprovalSection`.

Двойной submit блокируется. Закрытие модалки во время создания запрещено.

## Состояние и компоненты

- Логику формы, RBAC, payload и workflow сохранить в чистом модуле
  `maintenance-schedule-builder`.
- `MaintenanceScheduleBuilderDialog` владеет формой, queries, mutations и
  состоянием workflow. `PprCalendarPage` передаёт только `open`,
  `onOpenChange` и callback успешного завершения.
- Общий `MaintenanceScheduleBuilderForm` переиспользовать.
- Удалить неиспользуемые preview panel/table/summary и отдельный commit-dialog:
  в новом modal-flow нет ручного preview и вложенного подтверждения.
- Confirm-dialog поверх builder-dialog не нужен.
- Состояние формы сбрасывается только после успешного завершения или явного
  закрытия пользователем.

## Detail

Существующий detail builder-плана сохраняется:

- «Смешанный график»;
- `anchorMode`;
- вид ремонта и периодичность;
- плановая дата и относительный срок;
- fallback при недоступном enrichment-preview.

## Тестирование

### Backend

- options возвращает только оборудование, удовлетворяющее всем четырём
  критериям;
- каждый отсутствующий критерий исключает оборудование;
- type option отсутствует без подходящих единиц;
- `eligibleEquipmentCount` учитывает department scope;
- поиск, пагинация, сортировка и лимит `size`;
- RBAC/admin/wildcard и пользователь без подразделения;
- preview и options используют общий eligibility selector.

### Frontend

- toolbar-кнопка открывает modal;
- query-параметр открывает/закрывает modal без потери остальных фильтров;
- старый route перенаправляет в modal-flow;
- информационный блок содержит все четыре критерия;
- equipment/type options используют новый endpoint и infinite loading;
- пустое состояние объясняет eligibility;
- submit автоматически выполняет preview, затем create и approval;
- нулевой preview не создаёт план;
- ошибки preview/create сохраняют форму;
- частичный успех approval открывает detail с предупреждением;
- повторный submit заблокирован;
- паритет `ru`, `uz`, `en`.

## Критерии приёмки

- Пользователь не видит неподходящее оборудование или пустые типы в selector.
- Backend options, preview и task generation применяют одинаковые критерии.
- Модалка явно объясняет, почему часть оборудования скрыта.
- План с нулём рассчитанных работ не создаётся.
- Успешное действие создаёт задачи, отправляет план на согласование и открывает
  detail.
- Legacy PPR create-flow не изменён.
