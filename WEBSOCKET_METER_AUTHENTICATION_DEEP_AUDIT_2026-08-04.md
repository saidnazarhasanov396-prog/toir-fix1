# TOIR WebSocket Meter Authentication — Read-Only Deep Audit

**Audit date:** 2026-08-04 (Asia/Tashkent)  
**Scope:** supplied backend repository, locally available Git history, and one non-mutating production handshake probe  
**Constraint honored:** no production/test source, migration, dependency, branch, commit, push, build, or test change was made. This report is the only created file. No real JWT was used or recorded.

## 1. Executive summary

The reported browser symptom is an HTTP 401 during the WebSocket HTTP Upgrade, before `MeterRealtimeWebSocketHandler.afterConnectionEstablished` can run. In the audited backend HEAD, the originally suspected query-token extraction defect is **not present**: `JwtAuthenticationFilter` accepts `access_token` only for `GET /api/v1/ws/meters` when `Upgrade: websocket` is present, validates it through the ordinary `JwtService`, creates an authenticated Spring `Authentication`, and gives the `Authorization` header precedence. All other requests remain header-only.

The endpoint is not `permitAll`. There is one `SecurityFilterChain`; `/api/v1/ws/meters` has no special matcher and therefore falls under `.anyRequest().authenticated()`. A missing, malformed, expired, incorrectly signed, or otherwise rejected token leaves the request anonymous, after which `JwtAuthenticationEntryPoint` returns 401 before Spring's WebSocket handshake and handler. Once upgraded, the handler separately requires `METER_READ`, `SYSTEM_ADMIN`, or `*`; insufficient authority causes WebSocket policy close 1008, not the reported pre-upgrade HTTP 401.

A read-only production probe on 2026-08-04 used only the literal placeholder `<REDACTED>`. The response passed through `nginx/1.20.1` but contained the backend's exact JSON contract (`AUTHENTICATION_REQUIRED`, path `/api/v1/ws/meters`) and Spring security headers. Thus that probe's 401 was conclusively generated by Spring, not Nginx or the WebSocket handler. It also proves that the public route reaches this backend-style security layer and that `Origin` reaches Spring. Without a valid test token, production container commit identity, proxy configuration, proxy logs, and the frontend repository, the original user's exact cause cannot be distinguished among stale deployment, missing/expired/wrong-signature token, a proxy that fails to preserve the Upgrade header/query in some path, or frontend token lifecycle defects.

The current query-token support was introduced in commit `7f26e11710ba1bbcc2427e02135d8adfc13bfa66` on 2026-08-03. The leading operational hypothesis is that production/frontend state is not aligned with that contract, but this is **not verifiable from the supplied repository**. Do not add a second query-token implementation. First prove the deployed backend contains `7f26e117` or later, then compare direct-backend and proxy tests with the same newly issued, masked token.

**Final verdict: `INSUFFICIENT_EVIDENCE`**

## 5. Backend security trace

### Filter chain and ordering

`SecurityConfig.securityFilterChain` (`SecurityConfig.java:52-69`) creates a single stateless chain:

```java
.requestMatchers(PUBLIC_PATHS).permitAll()
.anyRequest().authenticated()
.authenticationEntryPoint(entryPoint)
.addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)
```

`/api/v1/ws/**` is absent from `PUBLIC_PATHS` (`SecurityConfig.java:25-35`) and has no separate matcher or chain. Therefore the HTTP Upgrade request must authenticate in the servlet filter chain before WebSocket mapping/handshake code runs.

### Extraction

`JwtAuthenticationFilter.extractToken` (`JwtAuthenticationFilter.java:104-119`) does exactly this:

1. Accept `Authorization: Bearer <token>` on any request.
2. Otherwise accept request parameter `access_token` only when all three predicates are true:
   - method is GET;
   - `request.getRequestURI()` equals `/api/v1/ws/meters`;
   - `Upgrade` header equals `websocket`, case-insensitively.
3. Otherwise return no token.

`JwtAuthenticationFilterWebSocketTest.java:27-61` asserts both endpoint scoping and header precedence. Ordinary `/api/v1/meters?access_token=...` remains anonymous.

### Validation and principal

`JwtService.parse` (`JwtService.java:61-66`) calls JJWT `verifyWith(key).parseSignedClaims(token)`. JJWT verifies signature and standard time claims such as `exp`; the code does not configure clock skew. The filter maps `primaryRoleCode`, `authorities`, and `permissions`, augments known role defaults, creates `AuthenticatedUser`, then creates `UsernamePasswordAuthenticationToken` and stores it in `SecurityContextHolder` (`JwtAuthenticationFilter.java:43-76`).

Important limits:

- `issuer` is emitted when TOIR generates a token (`JwtService.java:44-58`) but parsing does **not** call `requireIssuer`; issuer mismatch cannot explain a rejection by this code and is a validation-hardening gap.
- No audience is emitted or required; audience mismatch cannot explain a rejection by this code.
- No user repository/status lookup occurs during parsing. Deleted, disabled, or blocked user state is not checked for an otherwise valid unexpired token. Such state cannot explain this 401 in current code and is a revocation/status-enforcement gap.
- Invalid JWTs are caught as `JwtException`, logged only by exception class, and left anonymous (`JwtAuthenticationFilter.java:74-79`); authorization then produces 401.
- An explicitly empty query value may make JJWT throw an `IllegalArgumentException`, which the filter does not catch. That is a **POSSIBLE** 500-path robustness defect, not evidence for the observed 401.

### 401 and 403

Anonymous access invokes `JwtAuthenticationEntryPoint`, which returns HTTP 401 JSON (`JwtAuthenticationEntryPoint.java:26-40`). Authenticated HTTP access denied by Spring invokes `RestAccessDeniedHandler`, which returns HTTP 403 (`RestAccessDeniedHandler.java:26-40`). The WebSocket handler itself writes neither response.

## 6. WebSocket handshake trace

`MeterTelemetryWebSocketConfiguration.registerWebSocketHandlers` registers exactly `/api/v1/ws/meters` (`MeterTelemetryWebSocketConfiguration.java:40-46`). No custom `HandshakeInterceptor` or `HandshakeHandler` exists in the repository. Allowed origins come from the same `CorsProperties` used by HTTP CORS; production includes `https://toir.tenzorsoft.uz` (`application-prod.yml:43-49`). No servlet context path is configured, so the real backend path is `/api/v1/ws/meters`.

After successful HTTP authentication, Spring's standard servlet WebSocket handshake obtains the request principal and exposes it as `WebSocketSession.getPrincipal()`. The handler checks that principal in `afterConnectionEstablished` (`MeterRealtimeWebSocketHandler.java:38-45`). It accepts only authenticated principals with one of `METER_READ`, `SYSTEM_ADMIN`, or `*` (`MeterRealtimeWebSocketHandler.java:28-29,100-105`). Failure closes the upgraded WebSocket with `CloseStatus.POLICY_VIOLATION` (1008). Client text messages are rejected with 1003 (`MeterRealtimeWebSocketHandler.java:53-56`); this is a read-only notification channel.

There is defense in depth but two different failure stages:

- missing/invalid JWT → HTTP 401 before Upgrade;
- valid JWT without meter permission → HTTP 101, followed immediately by WebSocket close 1008.

**Observed break point:** the reported HTTP authentication failure is at `SecurityFilterChain → authenticated()` after extraction/validation failed to establish an `Authentication`, before origin/handshake/handler. The exact reason extraction/validation failed for the user's token is not available.

## 8. Confirmed root cause

The only root-cause statement supported at **CONFIRMED** level is the generic failure mechanism:

> At the failing handshake, no authenticated Spring `Authentication` exists by the time `.anyRequest().authenticated()` evaluates the request; Spring Security therefore rejects the HTTP Upgrade with 401 before any WebSocket handler code executes.

Evidence: `SecurityConfig.java:60-68`, `JwtAuthenticationFilter.java:43-79`, `JwtAuthenticationEntryPoint.java:26-40`, plus the live response matching that entry point.

The underlying reason that the original user's token did not create authentication is not confirmed. Current HEAD already implements the intended extraction contract, so labeling this HEAD with `CONFIRMED_BACKEND_TOKEN_EXTRACTION_DEFECT` would be false.

## 10. Security findings

1. **Query-token exposure — HIGH.** Full request targets may be recorded by Nginx access logs, load balancers, APM, Sentry breadcrumbs/network instrumentation, browser DevTools, support captures, and intermediary telemetry. `new WebSocket()` does not normally add a URL to ordinary navigation history, so conventional browser history exposure is lower, but session/history tooling may still capture it. TLS protects transit, not endpoint logs.
2. **Issuer/audience not enforced — MEDIUM.** A correctly signed token with an unintended issuer/audience is accepted. Add explicit issuer/audience requirements when token contracts are formalized.
3. **No user revocation/status check — policy-dependent MEDIUM.** Disabled/deleted users retain access until JWT expiry (default 720 minutes in config). Prefer short access tokens and a token-version/status strategy if immediate revocation is required.
4. **Long access-token lifetime — MEDIUM with URL transport.** `expiration-minutes: 720` increases the impact of query-log leakage.
5. **Mutable deployment tag — operational MEDIUM.** `latest` makes it hard to prove production code identity and can create source/runtime ambiguity.
6. **Blank-token exception handling — LOW.** Normalize with `StringUtils.hasText` and catch the parser's supported invalid-input exception family so malformed credentials always fail closed as 401.
7. **Positive controls — CONFIRMED.** Query extraction is exact-path/GET/Upgrade scoped, REST does not accept query JWT, real token values are not logged by the JWT filter, origin is restricted, handler rechecks permission, and browser writes are rejected.

## 12. Recommended minimal fix

The minimal safe fix is **Variant A as already implemented**, restricted to this endpoint. No new backend source edit should be made until deployment identity is checked.

1. Prove the production container/image contains commit `7f26e117` or later; preferably deploy HEAD `00435f3f...` by immutable image digest.
2. Configure the external proxy to preserve `Upgrade`, `Connection`, and query arguments for exactly `/api/v1/ws/meters`, and redact `access_token`/full request targets from access, error, APM, and Sentry logs.
3. Verify with a newly issued JWT that succeeds on REST and contains `METER_READ`, `SYSTEM_ADMIN`, or `*`. Run direct-backend then public-proxy tests with the same token.
4. In the frontend, retrieve the current access token for **every connection attempt** after refresh completion; reject missing/blank/`undefined`/`null`; use `encodeURIComponent` exactly once; discard sockets/retry timers on logout/unmount.
5. Preserve current header precedence and do not make `/api/v1/ws/**` `permitAll`.

This satisfies the stated constraints: exact meter endpoint only, ordinary validator, invalid/expired rejection, principal in session, permission preservation, no anonymous opening, and no token logging. If production already contains current HEAD and direct-backend valid-query authentication still fails, capture masked debug evidence before changing code.

## 13. Recommended production architecture

Adopt Variant C: an authenticated REST call mints an opaque, random, one-time WebSocket ticket with a 30–60 second TTL, stored only as a hash, bound to user, endpoint, and intended origin/audience. The handshake atomically consumes it and creates the same authenticated principal/authorities. The URL then contains a short-lived non-JWT ticket rather than a 12-hour bearer credential. Keep WSS, strict origins, rate limiting, replay detection, URL-log redaction, and normal REST JWT validation. Use immutable image tags/digests and expose a non-sensitive build commit in actuator info for deployment proof.

Separately harden JWT validation by requiring the configured issuer (and audience if adopted), deciding the disabled-user/revocation contract, shortening access-token lifetime, and defining small clock skew. These are security improvements, not proven fixes for this incident.
